# 增量抽取窗口的三种设计：回看重叠、高水位对齐与毒窗口熔断

*从「拉一段时间的数据」到「设计一个可信的时间契约」*

上一篇[《两只表的谎言》](/blogs/tech/zh/data-loading-window-two-clocks)讲了病：一条管道里墙上时钟和数据时钟错位，窗口对错了表，数据悄悄从缝里漏掉。这一篇讲药——真正把增量抽取窗口当成一个**设计问题**来对待，而不是随手写一行 `watermark_to = now`。

赫拉克利特说人不能两次踏进同一条河。增量管道的全部难处就在这里：你每次“踏进”的那条源数据河，水位一直在变——而且上游什么时候让你看到新水，往往不由你决定。窗口设计，本质上是在回答一个问题：**我凭什么相信“从 A 到 B 这段我已经看全了”？**

读完你会带走：

- 增量窗口的右边界，为什么**绑定墙上时钟永远是个潜在 bug**，哪怕今天还没炸；
- 回看重叠 vs 高水位对齐，两种修法各自的适用边界；
- 为什么**幂等 upsert 不是优化项，而是前置条件**——没有它，上面两种修法你一个都不敢用；
- 当某个窗口因为脏数据永远失败时，熔断器怎么让管道“跳过并前进”，而不是被一条数据永久卡死。

---

## 1. 右边界：你在相信哪一只时钟

先把上一篇的结论压成一句话：**增量窗口的右边界，应该是“我能可靠看到的数据的边界”，不是“我跑任务的时刻”。**

```python
# 反模式：右边界 = 墙上时钟
watermark_to = now_epoch

# 两种修法，都把右边界拉回到数据的时钟
# A. 对齐高水位
watermark_to = min(now_epoch, source_max_timemodified)
# B. 回看重叠（把左边界往回挪，容忍右边界冒进）
watermark_from = max(0, last_watermark_to - overlap_seconds)
```

**普通人的看法：** 用 `now` 很自然，“拉到现在”天经地义。
**资深工程师的洞察：** `now` 只在“源是实时的”这个前提下才等于数据边界。这个前提在实时 CDC 里成立，在每日快照 / 定时加载 / 有复制延迟的只读副本里**全部不成立**。所以 `watermark_to = now` 不是“错”，是“埋了一颗引信”——哪天上游改成批量加载、或者副本延迟变大，它就炸。

> 第一性原则：窗口的边界是数据的属性，不是调度器的属性。把它绑在 `now` 上，等于把数据正确性抵押给了“上游永远实时”这个你并不拥有的假设。

---

## 2. 两种修法的边界：对齐高水位 vs 回看重叠

两种都对，但适用场景不同。别死记，记住各自的代价：

| 维度 | 对齐高水位（watermark_to = MIN(now, MAX(src))) | 回看重叠（watermark_from 往回 overlap） |
|---|---|---|
| 正确性 | 精确——只读进已到达的数据，一行不漏不丢 | 最终一致——漏掉的会在后续窗口被重新捞回 |
| 额外读 | 几乎没有，每源多一次 `MAX()` | 每次多读 overlap 窗口内已同步的数据 |
| 依赖 | 要能查到源的真实水位时间戳 | 要下游幂等（否则重复写） |
| 改动面 | 碰抽取核心逻辑，每源都要接 | 一个参数 + watermark 起点一行改动 |
| 顺带好处 | 无 | 自动回灌修复上线前漏掉的历史数据 |
| 失效场景 | 源没有可信的“最后更新时间”列 | overlap 短于实际延迟，仍会漏 |

**决策口诀：**
- 能拿到源的可信水位、且追求“零冗余读 + 精确” → 对齐高水位。
- 下游已经是幂等 upsert、想要最小改动且顺手补历史 → 回看重叠。
- 两者都做也行：高水位保正确，小 overlap 兜住“水位时间戳本身也有延迟”的二阶误差。

我上一个 case 选了回看重叠，就是因为下游是基于外部唯一键的 Bulk upsert，改动面只有一行，还白捡了一次历史回灌。overlap 取 48h，是“上游最坏延迟约 1 天 + 1 天冗余”。

> 直觉口诀：高水位是“我只拿我看全的”，重叠是“我宁可多拿一遍，反正写进去不重复”。

---

## 3. 幂等 upsert：一切回读的前提

上面两种修法，回看重叠显式地重读数据，高水位在重试时也会重读同一个窗口。只要你会重读，**下游就必须幂等**，否则每一次“回头”都在制造重复行。

幂等的来源是一个**外部唯一键**——用源系统里那条记录天然的、稳定的 ID，而不是自增主键或哈希：

```text
upsert 的 externalId = 源成绩记录的 grade_id
→ 同一条成绩无论被同步多少次，命中的都是下游同一行，覆盖成同样的值
```

| 没有外部唯一键 | 有外部唯一键 |
|---|---|
| 回读 = 重复行，数据越滚越脏 | 回读 = 幂等覆盖，无害 |
| 不敢重叠、不敢重试、不敢回灌 | 重叠/重试/回灌全部变成安全操作 |
| “只跑一次”成了正确性的隐含前提 | 正确性不再依赖“恰好一次” |

**面试拿分点：** “exactly-once”在分布式系统里极其昂贵且脆弱；工程上真正可落地的，是“at-least-once 投递 + 幂等接收”。你把去重的责任从“传递通道”挪到了“接收端的唯一键”，整条管道的容错设计瞬间简单一个量级。这也是为什么我说幂等不是优化，是前置条件——它是你敢用上面所有“重读”手法的那张许可证。

> 一句话哲学：幂等不是用来防重复的，是用来**换取重试与回读的权利**的。

---

## 4. 毒窗口：让熔断器替你做取舍

最后一个真实问题：如果某个窗口里就是有一条下游永远拒绝的脏数据（字段超长、外键对不上、picklist 非法值），会怎样？

朴素实现：窗口失败 → 下次重试同一窗口 → 又失败 → 永远卡在这里，watermark 再也不前进。一条脏数据，顶死了整条管道。

成熟实现是一个**熔断器 + 死信隔离**的组合：

```text
窗口失败 → retry_count + 1 → 重试同一窗口
到达 max_retry → 不再死磕：
    · 把这一批失败行写进 DLQ（留证据，可离线修）
    · 把这个窗口标成 PARTIAL（部分成功/跳过）
    · watermark 照常前进，不让一条脏数据永久阻塞后续
```

| 没有熔断器 | 有熔断器 |
|---|---|
| 一条脏数据 = 整管道永久停摆 | 脏数据被隔离进 DLQ，主流继续走 |
| watermark 永远卡在毒窗口前 | watermark 越过毒窗口，后续数据照常同步 |
| 故障靠人半夜被叫醒手动跳过 | 故障降级为“DLQ 里有 N 行待处理”的异步工单 |

这里的设计哲学，是把“部落知识”变成“工程产物”：**“这个窗口有脏数据，手动跳过它”本来是只存在于某个老工程师脑子里的口头经验，熔断器把它固化成了代码里一条确定的规则。** 代价是你要接受“最终一致 + 人工补 DLQ”，换来的是管道不会被单点脏数据永久拖死。

> 直觉口诀：好的管道不是永不失败，而是**失败能被隔离，而且不阻塞健康的数据**。

## 立刻可以做的事

1. 审一遍你的增量管道，给每一条回答两个问题：右边界绑的是 `now` 还是数据水位？下游是不是基于外部唯一键的幂等 upsert？两个答案决定了你能不能安全地重读。
2. 如果下游还不是幂等的，这是比“修窗口”更优先的事——先把外部唯一键建起来，否则任何重读修法都会制造重复。
3. 给每条管道加熔断：定义 `max_retry`，到达后写 DLQ + 标 PARTIAL + 推进 watermark，别让单点脏数据永久阻塞。
4. 把 overlap / max_retry 这些值做成配置项（变量，而不是硬编码）——它们是你未来调参的旋钮，也是把“部落知识”落成“工程产物”的载体。
