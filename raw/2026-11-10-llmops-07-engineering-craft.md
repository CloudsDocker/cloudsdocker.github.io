# LLMOps 实战 07：工程手感

> 君子之过也，如日月之食焉：过也，人皆见之；更也，人皆仰之。

前六篇讲的是设计。这一篇讲做的过程里那些不起眼的决定：一个合并冲突怎么解，hook 拦住提交时怎么办，往一千多行的文件里插代码怎么保证没碰坏别的。

设计文档里不会有这些。但一个项目「感觉靠谱」还是「感觉悬」，多半取决于这一层。

---

### 1. 🎯 30 秒版本

- 解冲突前先问：这是**二选一**，还是**两边各加了东西**？
- 报错信息和真实状态矛盾时，信真实状态。
- 安全检查拦住你时，修原因，不要绕过检查。
- 改大文件用「断言唯一匹配再替换」，替换不上就当场失败。
- 重构要能**证明**没改行为，不要靠评审的人相信。
- 顺手发现的 bug：一行能修的修掉并说明，其余的只报告。

---

### 2. ⚙️ 一件一件说

#### 2.1 合并冲突：先分类，再动手

四个文件冲突，看一眼就能归类：

```
<<<<<<< HEAD
from portal_api.routers import chat, history, traces
=======
from portal_api.routers import chat, english, history
>>>>>>> origin/main
```

一边加了 `traces`，另一边加了 `english`。这不是冲突，是两个人在同一行上各加了一个东西。答案是 `chat, english, history, traces`。

另外三个文件同理：两个互不相干的方法被加在了同一个位置；两段互不相干的提示词被加在了同一个位置。判断依据是**两段代码是否互相依赖、条件是否互斥**，不是哪边「看起来更新」。

只有一处需要真正合并语义：一边把变量 `name` 改成了更准确的 `target_tool`，另一边在同一段加了 trace 记录且还在用 `name`。这里要取后者的新增逻辑、套上前者的变量名。

**顺序：先处理机械的，再处理需要思考的，最后跑全量测试。** 合并后测试挂了三个，逐个确认：两个是本机没装 pandoc，一个是主干上本来就有的 bug。都不是合并引入的——这句话要有依据才能说，依据是去主干分支上看那一行。

#### 2.2 hook 回滚：信状态，不信报错

提交时 pre-commit 的空白修复 hook 想改一个文件，和暂存区冲突，于是「回滚修复」，提交失败。再提交，再失败。

这时候报错信息基本没用。有用的是三条命令：

```bash
ls .git/MERGE_HEAD          # 合并还在进行中吗
git diff --name-only        # 工作区和暂存区差在哪
git diff -w --quiet -- <file> && echo whitespace-only
```

答案是：hook 的修复其实留在了工作区，只是没进暂存区，而且差异纯粹是空白。把它 `git add` 进去，提交就过了。

> 经验：工具说「失败了」的时候，去看它**留下了什么**。重试之前先搞清楚上一次到底改变了哪些状态。

#### 2.3 扫描器拦住你：修原因

密钥扫描器两次拦住了提交，两次的处理不一样，值得对比。

**第一次**，命中的是主干上的一行类型注解：一个名字里带 token 的变量后面跟着 `: list[str] = []`。这是扫描规则的盲区，于是给规则加了一条带注释的豁免：类型注解不是凭据。改的是规则，影响是全局的，所以注释里写清楚了为什么。

**第二次**，命中的是我自己新写的文件：策略文件里一个键名撞了关键字，评测数据里有故意伪造的假 token。这次我想再加一条路径豁免，被拒了。

回头看，被拒是对的。第二次的问题出在**我的文件长得像密钥**，不在扫描器。正确的修法是让文件不再像：

- 策略里的键改名为 `key_material`。
- 数据集里只用云厂商文档公开的示例 key（扫描器本来就认识它）。
- 其它形态的 token 挪到单测里，运行时拼接：

```python
@pytest.mark.parametrize("rule_id, token", [
    # 运行时拼出来，仓库的密钥扫描器不会把这些夹具当真
    ("SEC-GITHUB-TOKEN", "ghp_" + "a1B2c3D4e5F6" * 3),
    ("SEC-PRIVATE-KEY", "-----BEGIN " + "RSA PRIVATE KEY-----"),
])
```

区别在于：**放宽一条安全规则，受益的是今天的我，承担风险的是以后所有人。** 能通过改自己解决的，就不该去改规则。

`--no-verify` 从头到尾没出现过。

#### 2.4 往大文件里动刀：断言式替换

agent 主循环那个文件一千三百多行。往里面加五处改动，最怕的是替换到了错误的位置，或者某处没替换上而自己不知道。

```python
def rep(old, new, count=1):
    global s
    assert s.count(old) == count, (old[:60], s.count(old))
    s = s.replace(old, new)
```

每一处替换前都断言「旧文本恰好出现一次」。出现零次——锚点写错了；出现两次——锚点不够具体。无论哪种都立刻失败，不会留下一个改了一半的文件。

选锚点也有讲究：选**这段代码独有的、语义稳定的那几行**，不要选可能到处都有的片段。

#### 2.5 重构要自带证明

把系统提示词从 Python 常量搬到版本化文件，理想的评审意见是「不需要看内容」。怎么做到：

```python
(base / "agent_steering/v1.md").write_text(agent.STEERING)        # 程序导出，不手抄
assert registry.get("agent_steering").text == agent.STEERING      # 删常量之前先断言
```

然后跑全量测试，三百多个既有测试一个不变。这次改动对模型行为的影响被证明为零。

同样的思路贯穿全程：接入 guardrail 之后，第一件事是跑**既有的**全部测试，确认默认策略没有误伤任何已有流程。新功能的测试放在后面。

#### 2.6 看见不属于自己的问题时

过程中碰到了三件不在需求里的事：

- 主干上一个函数用了 `ast` 却没 import，导致一个测试必挂。**一行能修、且不修就没法得到一个干净的测试结果**——修了，并在总结里单独说明这不是合并引入的。
- 一个文档软链接指向了不存在的路径。它会让目录扫描抛异常，所以代码里跳过了不是普通文件的路径；链接本身没动，只在总结里报告。
- 依赖锁文件被全局 gitignore 了，CI 每次都重新解析依赖。这是别人的决定，可能有原因。没动，写进了已知问题。

判断标准：**挡路的且修起来明确的，修；不挡路的或者意图不明的，说。** 「顺手优化」是最容易让一个 PR 变得无法评审的习惯。

#### 2.7 验证要对着真实环境的形状

验证实时调用栈时，特意让 agent 跑在**另一个进程**里，API 进程只负责推送。因为线上就是两个进程；在同一个进程里验证通过，什么也证明不了。

同理，本机没有数据库，正式服务起不来。没有硬凑一个数据库，而是写了个十行的临时入口，只挂载要验证的路由，数据目录指到临时位置，不污染真实数据。验证完就删。

还有一条反向的：部署环境不是手头这台机器时，在手头机器上验证到「够用」就该停。把代码写完、把要在目标机器上执行的步骤列清楚，比在错误的机器上追求完美更有价值。

### 3. 🧭 这些习惯背后的同一个想法

| 做法 | 背后的想法 |
|---|---|
| 冲突先分类 | 理解意图，而不是处理文本 |
| 看真实状态 | 报错是线索，不是结论 |
| 不绕过扫描器 | 不把自己的方便变成别人的风险 |
| 断言式替换 | 让错误当场发生 |
| 逐字节等价 | 用证明代替信任 |
| 只修挡路的 | 一个改动只做一件事 |
| 按部署拓扑验证 | 测真正会出问题的地方 |

如果只能记一条：**让错误尽早、尽响地发生。** 断言、gate、变异测试、`known_gap` 通过时反而失败——全是同一个想法在不同层面的样子。

### 4. 🔬 常见追问

**Q：断言式替换和直接用编辑器改有什么区别？**
单处修改没区别。一次改五六处、且它们必须同时成立时，脚本的好处是原子性：要么全部成功，要么在第一处出问题时停下。而且整个改动是可重放的。

**Q：什么时候应该放宽一条检查规则？**
当问题确实出在规则上，而且放宽的范围可以写得很窄、理由可以写成注释时。如果你发现自己想豁免一整个目录，先问一遍能不能改内容。

**Q：合并后测试挂了，怎么快速判断是不是合并引入的？**
到合并前的两个父提交上分别看那段代码。两边都有的问题不是你引入的。这比读测试输出快得多。

### 5. 🛠 自己动手

1. 下次遇到冲突，先写下每一处属于「二选一」「两边都留」还是「语义合并」，再动手。
2. 写一个带唯一性断言的替换脚本，用它完成你的下一次多处修改。
3. 找一次你做过的重构，想一想：当时有没有办法**证明**行为没变？
4. 翻翻你的提交历史里有没有 `--no-verify`。每一次背后，被绕过的那个检查想告诉你什么？
5. 画出你的系统在生产环境的进程和机器分布，再对照一下你平时是在什么拓扑下做验证的。
